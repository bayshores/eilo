# Why felis still feels manual

Research and source audit, September 9, 2026. Status: findings and a proposed next increment; no runtime migration, new tools, monitoring, permissions or model calls were enabled.

**The gap is structural. felis uses Hermes for a constrained conversational/task transaction and a small activity-to-check-in path, while much of the surrounding agent capability remains unused.** Connecting Chrome is necessary for the current observation feature, but does not by itself deliver the requested experience of an assistant that keeps up throughout the day. The recommendation is to retain Hermes, make a bounded integration with its persistent custom-client interface, and give it useful, permissioned context and app-specific operations. Preserve the accepted UI and existing task/history guarantees.

The user wants to spend less effort noticing, remembering, reporting and initiating. More notifications, a busier activity indicator, or more task controls would not establish that outcome. This interpretation follows the current feedback; its effectiveness still needs direct use.

## Recommended next increment

**One assistant-maintained context and outreach loop, built around the existing Hermes foundation.** Keep the accepted frontend. Prototype this as an isolated integration before changing the live runtime.

**User clarification, September 9:** agent-initiated outreach is a core requirement alongside the harness capabilities. The user must not have to send a new message or return to a dashboard to elicit needed help. Context upkeep supports the decision to reach out; it is not a substitute for reaching out. A meaningful permitted signal, unresolved need or agreed follow-up should cause a brief, useful intervention when warranted. Delivery while the user is elsewhere needs an explicitly permitted channel and a working background lifecycle; neither is silently enabled by this clarification.

1. **Keep intentions between sessions.** Ordinary conversation should maintain current goals, corrections, accepted plans, breaks and unresolved questions. Augment the working task/transcript foundation with compact, app-owned context where needed. Do not require a fresh daily goal form. A newly inferred activity relationship remains a suggestion; it does not silently become a commitment.
2. **Give Hermes narrow access to that context.** Test its documented persistent custom-host protocol with explicitly scoped read operations for felis's own goals, remembered preferences and permitted context. Retain the existing transaction validator for state changes. Do not simply turn on every native tool or load unrelated local folders. Protocol choice and exact tool inventory belong in the bounded integration specification.
3. **Reconcile observations before asking the user.** Locally merge repeated samples, retain source and freshness, relate them to known intentions where warranted, and prepare a concise account of what changed. Keep observed activity, tentative interpretation and confirmed outcomes distinct. An approved result signal could support a later completion adapter; a page title or elapsed duration cannot.
4. **Use meaningful changes to decide when to speak.** A return to the app, accepted context change, unresolved question or explicitly requested follow-up can be a decision point. Low-frequency maintenance can keep state current without producing a notification. Preserve preemption, correction, breaks, cooldowns and budgets. The ordinary outcome should often be a useful silent update to separately labeled observation/context records. That does not silently change goals, focus, breaks or completion. A later authorized result-source rule could maintain supported task fields through validated transactions without asking for every routine update; no such new rule is approved by this research.
5. **Show the work felis actually did.** A compact view should expose the last observed source/freshness, what was carried forward or revised, and any one thing needing clarification. Keep detail and correction available without a blocking chat. Existing Activity and Home components provide the starting point. This is a proposed interaction, not a request for another aesthetic redesign or fake activity animation.

Example acceptance scenario: the user states a practice intention once and works elsewhere. In one case with a supported reason to intervene, felis initiates and delivers a useful check-in without another user message or opening Home; the reply returns to the same context. In a second case where help is not warranted, felis stays quiet and maintains an attributed summary for later inspection. A disabled or unavailable delivery channel must be distinguishable from deliberate silence. The current in-Home presentation alone does not pass the first case. No daily re-entry or manual session log is required. A correction changes the interpretation durably and prevents the same mistaken follow-up. A related page does not increment solved-problem count. If no new information warrants interruption, the assistant stays quiet while keeping its visible context current.

This is more than the earlier recommendation to switch on Chrome and test the existing loop. That trial remains useful for the collector, but cannot validate capabilities the current architecture does not implement.

## Verification gate and remaining decisions

The first experiment should use a separate synthetic session, preserve the current native history and task-publication contract, and exercise ordinary updates, useful silence, correction, break/cancel, interrupted runs, stale events, restart and compaction. Verify one owner for session writes, durable acceptance, commit-before-acknowledgment and no repeated inference after uncertain delivery. A live gateway must not run concurrently with the old per-turn writer against the same real session. The protocol may supply more capabilities than the product should expose.

Measure whether a warranted check-in is initiated and actually delivered without a fresh message or dashboard visit; fewer repeated goal explanations and manual reports; correctness of carried-forward state; supported vs fabricated claims; unwanted/missed interruptions; recovery; response latency and model usage. Test actual permitted activity only after the isolated path works. No arbitrary numerical success threshold or claimed productivity benefit is established by this audit.

The pending permission to send recent multi-session summaries to Luna remains unanswered. Research does not approve that flow. New background collection, broader sources, app-specific tools that expose new data, or a persistent monitoring service must have their scope made concrete before activation. The current provider and billing boundary remain unchanged.

## Confidence, counterevidence and search scope

**High confidence:** the local restrictions, retained native history, task transaction boundary, narrow activity lifecycle and public data limits, because both direct source reading and an independent adversarial audit established them. **Moderate confidence:** these omissions explain much of the user's dissatisfaction and the proposed loop would reduce upkeep; that is a product hypothesis, not measured behavior. No evidence here establishes that switching models or harnesses alone would improve satisfaction.

Three independent read-only lanes checked Hermes, OpenClaw, and context-aware companions; a fresh local-code audit challenged the integration diagnosis. The coordinator checked current felis source, the original shortlist, HealthMes/CatchMe primary source, and the decision-critical counterclaims. Final targeted searches of custom-client/session semantics, standing-intent matching, activity import wiring and context-processing/feedback paths did not change the recommended next decision.

Hermes was checked against the installed immutable revision in `hermes-source.json`; HealthMes and CatchMe were checked at the immutable revisions linked above. Other comparator code was inspected on current main or live official documentation and may lead released packages. A guessed MineContext config URL was unavailable; no conclusion relies on it. Some GitHub/raw browser fetches failed; HealthMes/CatchMe exact files were verified through public GitHub API/raw reads. No third-party code was executed. This was a bounded technical comparison, not an exhaustive product search, new install, real activity trial, microphone test, speed benchmark, cross-device demonstration or psychology efficacy study.

The earlier general-product candidates such as Focus Bear were not re-evaluated as install-ready replacements in this pass. Their historical comparison remains in the private planning note; no current reliability or superiority claim is made.
